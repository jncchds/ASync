## The person's goal and the agreed design
Back up the iPhone's photos and videos exactly as Android does since task 19: a Photos Backup folder, the per-device selection (all, or chosen albums; filters since date, videos, screenshots) made in the web UI from the album list the phone reports over the hub (live, or the last reported list), originals as they are with the JSON sidecar, deletions kept per retention, restore back into the library and albums skipping what is there. **Server, Contracts shapes and the repository/sidecar format must not change**: reuse `IMediaLibrary`, `MediaTree`, `MediaLayout`, `MediaSidecar`, `MediaRestorer`, the albums hub request and `PUT /api/sync/media/albums`, `PhotosViewModel`/`PhotosView`. The sidecar's `source` is `ios-photokit` (already anticipated by the format).

## Scope
1. **`IMediaLibrary` over PhotoKit** in the iOS head, following the iOS mapping notes: `PHAsset.localIdentifier` → id (short id with `/` → `_`), user albums and the useful smart albums (Favorites, Screenshots, Videos…; decide which and document) → albums with counts, an asset in several albums listing them all; `PHAssetResource`s → roles (`original`, `live` for `.pairedVideo`, `edited` for full-size edits, `raw` for `.alternatePhoto`), read with `PHAssetResourceManager.requestData` streamed to the tree without loading whole videos into memory; dates, size, duration, location, favourite, screenshot subtype; `relativePath` empty. Keep the PhotoKit calls behind a thin interface so the mapping logic is plain C# and unit-tested on Linux.
2. **Authorisation:** `.authorized` = Full, `.limited` = Partial (the app explains and offers `presentLimitedLibraryPicker`; the web UI already shows Partial), denied/restricted = None with the same "no permission stops the run" behaviour as Android; `NSPhotoLibraryUsageDescription` and `NSPhotoLibraryAddUsageDescription` (add only for restore) with clear texts; ask at the same moments the Android app does.
3. **iCloud originals:** assets whose originals are only in iCloud ("Optimize iPhone Storage"): network access allowed for PhotoKit downloads, with a per-device or per-folder option, in the existing selection model if it fits without a format/Contracts change, otherwise as a local app setting — decide, document; respect the folder's run conditions (Wi-Fi only also applies to iCloud downloads); an asset that cannot be fetched now is skipped and retried, not reported as deleted.
4. **New photos:** a `PHPhotoLibraryChangeObserver` while the app runs triggers the Photos folders (debounced); in the background the task 22 BGProcessing/BGAppRefresh plan includes Photos folders; persistent change tokens (`PHPersistentChangeToken`, iOS 16+) to skip unchanged libraries cheaply if that fits, otherwise the existing "unchanged originals are not read again" logic.
5. **Restore into the library:** `MediaRestorer` with `PHAssetCreationRequest` (original, paired video as `.pairedVideo` for Live Photos, the date and location from the sidecar), into the albums named in the sidecar (create missing user albums), skipping assets already present as Android does; add-only permission asked only for restore.
6. **Adding Photos folders from the app** (task 18 flow) and the hub album list work on iOS (`DeviceBrowseState.Media` reported correctly; `FolderService.HasPhotoLibrary` already accepts iOS — check it).
7. **Tests on Linux:** the PhotoKit mapping (roles from resource types, ids, smart albums, subtypes, dates/UTC, multi-album assets) against a fake of the thin interface; authorisation mapping; iCloud-unavailable assets skipped and not deleted; restore planning (albums created, existing skipped, Live Photo pairs); the change-observer debounce; `MediaBackupTests` still pass with `ios-photokit` sidecars. Both test projects pass.
